## I — Предисловие

Римские инженеры вырезали каменные таблицы с идеальными сетками для отслеживания поставок зерна по всей империи, чтобы ни одна доставка не была потеряна из-за плохого почерка. В 1800-х годах моряки записывали океанские течения в структурированных таблицах настолько точно, что некоторые из них используются в навигации по сей день.

Первые прогнозы погоды передавались в виде телеграмм в фиксированном коде — нескольких чисел, способных описать целое небо. В 1960-х годах центр управления полётами NASA работал по ламинированным блок-схемам, которые точно указывали, что означает каждый мигающий индикатор, независимо от того, кто был на смене. Сканеры штрих-кодов в супермаркетах переводили чёрно-белые полоски в инвентаризационные данные задолго до того, как в большинстве домов появились компьютеры. Даже пчеловоды десятилетиями использовали стандартизированные формы, записывая состояние ульев, поток нектара и родословную маток в крошечных клетках, которые мог прочитать с одного взгляда только они.

Люди всегда создавали структуры, чтобы сделать информацию надёжной, доступной для обмена и пригодной к использованию. Что приводит нас к сегодняшнему дню, где цель — заставить ИИ говорить на языке компьютеров.

## III — Введение

### III.1 — Что такое вызов функций?

Большие языковые модели (LLM) отлично понимают и генерируют человеческий язык, но они не создают структурированный, исполняемый машиной вывод естественным образом. Вызов функций (Function Calling) ликвидирует этот разрыв, преобразуя запросы на естественном языке в точные вызовы функций с типизированными аргументами.

Рассмотрим пример: Преобразование естественного языка в вызов функции

> **Пользователь:** «Какова сумма 40 и 2?»
>
> **Обычный LLM:** «Сумма 40 и 2 равна 42.»
>
> **Система вызова функций:**
> ```json
> {
>   "function": "add_numbers",
>   "arguments": {"a": 40, "b": 2}
> }
> ```

Система вызова функций не отвечает на вопрос напрямую. Вместо этого она предоставляет инструменты для решения: правильное имя функции и корректные аргументы с правильными типами.

### III.2 — Почему это важно?

Вызов функций позволяет LLM:

- **Взаимодействовать с внешними системами:** вызывать API, выполнять запросы к базам данных, управлять устройствами
- **Выполнять код:** производить вычисления, трансформации данных, операции с файлами
- **Выстраивать цепочки операций:** разбивать сложные задачи на исполняемые шаги
- **Предоставлять структурированный вывод:** генерировать JSON, XML или другие машиночитаемые форматы
- **Извлекать структурированные данные из неструктурированного текста:** например, из большой книги извлечь поля вроде `{имя_главного_героя, пол_главного_героя, возраст_главного_героя}`

Эта технология лежит в основе современных ИИ-ассистентов, инструментов генерации кода и автономных агентов, а также позволяет выполнять задачи по автоматическому извлечению информации и структурированию знаний из сырого текста.

### III.3 — Задача

Маленькие языковые модели (например, модель с 0.6B параметров, которую вы будете использовать) печально известны ненадёжностью при генерации структурированного вывода. При запросе на создание JSON они могут добиться успеха лишь в 30% случаев. Однако продакшн-системы достигают 99%+ надёжности с теми же маленькими моделями.

Как? Ответ — **ограниченное декодирование** (constrained decoding) — техника, которая направляет вывод модели токен за токеном для гарантии правильной структуры, не полагаясь только на промптинг.

## IV — Общие инструкции

### IV.1 — Общие правила

- Проект должен быть написан на **Python 3.10** или более новой версии.

- Проект должен соответствовать стандарту кодирования **flake8**.

- Функции должны корректно обрабатывать исключения, чтобы избегать сбоев. Используйте блоки `try-except` для управления потенциальными ошибками. Предпочитайте контекстные менеджеры для ресурсов, таких как файлы или подключения, для обеспечения автоматической очистки. Если программа аварийно завершается из-за необработанных исключений во время проверки, она будет считаться нефункциональной.

- Все ресурсы (например, дескрипторы файлов, сетевые подключения) должны управляться надлежащим образом для предотвращения утечек. Используйте контекстные менеджеры там, где это возможно, для автоматического управления.

- Код должен включать **аннотации типов** для параметров функций, возвращаемых типов и переменных, где это применимо (используя модуль `typing`). Используйте `mypy` для статической проверки типов. Все функции должны проходить проверку mypy без ошибок.

- Включите строки документации (docstrings) в функции и классы в соответствии с **PEP 257** (например, в стиле Google или NumPy) для документирования назначения, параметров и возвращаемых значений.

## V — Обязательная часть

### V.1 — Описание

В этом проекте вы создадите инструмент для вызова функций, который преобразует запросы на естественном языке в структурированные вызовы функций. Получив вопрос вроде «Какова сумма 40 и 2?», ваше решение должно вернуть не `42`, а:

- **Имя функции:** `fn_add_numbers`
- **Аргументы:** `{"a": 40, "b": 2}`

Ваша реализация должна использовать **ограниченное декодирование** для гарантии 100% валидного JSON-вывода, обеспечивая практически идеальную надёжность даже с небольшой моделью на 0.6B параметров.

### V.2 — Входные файлы

Ваше решение будет обрабатывать два входных файла, расположенных в каталоге `data/input/`:

- **function_calling_tests.json:** содержит JSON-массив запросов на естественном языке, которые ваша система должна обработать.

  Пример: `function_calling_tests.json`

- **functions_definition.json:** содержит доступные функции, которые ваша система может вызывать. Каждая функция включает:

  - Имя функции
  - Имена и типы аргументов

### V.3 — Взаимодействие с LLM

#### V.3.1 — LLM SDK

К этому проекту прилагается класс-обёртка `Small_LLM_Model` из пакета `llm_sdk`, который можно использовать для взаимодействия с LLM.

SDK предоставляет несколько основных методов:

- **`get_logits_from_input_ids(input_ids: List[int]) -> List[float]`**
  Принимает список ID токенов и возвращает логиты, сгенерированные моделью LLM.

- **`get_path_to_vocab_file() -> str`**
  Возвращает путь к файлу словаря, содержащему соответствие между ID токенов и самими токенами.

- **`encode(text: str) -> Tensor`**
  Кодирует текстовую строку в тензор ID токенов с помощью токенизатора модели.

- **`decode(token_ids: List[int]) -> str`** (необязательный)
  Опционально декодирует список ID токенов обратно в текстовую строку.

#### V.3.2 — Конвейер генерации

Процесс генерации LLM включает следующие шаги:

1. **Промпт:** Ваш вопрос на естественном языке
   Пример: `"What is the sum of 2 and 3?"`

2. **Токенизация:** Текст разбивается на подсловные единицы (токены). В отличие от простого разбиения по словам, токенизаторы часто включают ведущие пробелы, обрабатывают пунктуацию и разбивают слова на более мелкие компоненты с помощью алгоритмов, таких как BPE или SentencePiece.
   Пример (реалистичный): `["What", "Ġis", "Ġthe", "Ġsum", "Ġof", "Ġ2", "Ġand", "Ġ3", "?"]`
   Примечание: Символ `Ġ` обозначает предшествующий пробел; реальные токенизаторы сохраняют такие детали для точного восстановления текста.

3. **Входные ID:** Токены преобразуются в числовые идентификаторы, которые понимает модель.
   Пример (иллюстративный): `[892, 318, 262, 4771, 286, 16, 290, 17, 30]`

4. **Обработка LLM:** Модель обрабатывает эти числа через свою нейронную сеть.

5. **Логиты:** Модель выдаёт оценки вероятностей для каждого возможного следующего токена.
   Пример: `token_5: 0.001, token_42: 0.85, token_100: 0.02, ...`

6. **Выбор токена:** Следующий токен выбирается на основе этих вероятностей, обычно тот, который имеет наивысшую оценку.
   На этом этапе могут применяться техники вроде **ограниченного декодирования** для ограничения выбора токенов и обеспечения того, чтобы вывод следовал определённой структуре, например, для генерации 100% валидного JSON.

> [!IMPORTANT]
> Этот процесс повторяется **токен за токеном**. Каждый сгенерированный токен добавляется к промпту, и шаги 2–6 повторяются до тех пор, пока не будет сгенерирован полный ответ.

**Упрощённая схема:**
```
Промпт -> Токенизация -> Входные ID -> LLM -> Логиты -> Выбор следующего токена
```

#### V.3.3 — Понимание ограниченного декодирования

Языковые модели генерируют текст по одному токену за раз. На каждом шаге модель создаёт распределение вероятностей (логиты) по всем возможным следующим токенам. Обычно из этого распределения производится выборка или выбирается токен с наивысшей вероятностью.

Ограниченное декодирование вмешивается в этот процесс, **модифицируя логиты перед выбором токена:**

1. Модель создаёт логиты для всех возможных токенов.

2. Вы определяете, какие токены сохранят как валидную JSON-структуру, так и соответствие ожидаемой схеме.

3. Вы устанавливаете логиты для невалидных токенов (тех, которые нарушают схему или структуру) в **минус бесконечность**.

4. Вы производите выборку только из оставшихся валидных токенов.

В этом проекте ограниченное декодирование должно не только обеспечивать синтаксически валидный JSON, но и **обеспечивать соответствие определённой схеме**. Например, если поле ограничено числом в `functions_definition.json`, декодер ограничивает выбор токенов значениями, удовлетворяющими целому числу или числу с плавающей точкой, сохраняя как валидность JSON, так и соответствие схеме. Это гарантирует, что каждый сгенерированный токен поддерживает как структурную, так и семантическую валидность, обеспечивая соблюдение требуемой схемы. В результате созданный JSON на 100% пригоден для извлечения и может быть разобран без ошибок.

> [!CAUTION]
> Ваше решение **НЕ ДОЛЖНО** полагаться на то, что модель самопроизвольно создаёт корректный JSON из промпта. Промптить модель определениями функций и надеяться на структурированный вывод ненадёжно, и это не тот навык, который мы ожидаем от вас здесь.

> [!TIP]
> Подумайте, как использовать JSON-файл словаря для сопоставления между токенами и их строковыми представлениями. Это критически важно для определения того, какие токены являются валидными на каждом шаге генерации.

### V.4 — Формат выходного файла

Ваша программа создаст единственный JSON-файл: `data/output/function_calling_results.json`.
Для каждого промпта добавьте JSON-объект в этот файл. Каждый объект в массиве должен содержать ровно следующие ключи:

- **prompt** (string): Исходный запрос на естественном языке
- **name** (string): Имя вызываемой функции
- **parameters** (object): Все обязательные аргументы с правильными типами

#### V.4.1 — Пример вывода

```json
[
    {
         "prompt": "What is the sum of 2 and 3?",
         "name": "fn_add_numbers",
         "parameters": {"a": 2.0, "b": 3.0}
    },
    {
         "prompt": "Reverse the string 'hello'",
         "name": "fn_reverse_string",
         "parameters": {"s": "hello"}
    }
]
```

#### V.4.2 — Правила валидации

- Файл должен быть валидным JSON (без висячих запятых, без комментариев)
- Ключи и типы должны точно соответствовать схеме в `functions_definition.json`
- Никакие дополнительные ключи или текст не допускаются нигде в выводе
- Все обязательные аргументы должны присутствовать
- Типы аргументов должны соответствовать определению функции (number, string, boolean и т.д.)

> [!WARNING]
> Данные входные файлы могут измениться во время рецензирования. **Не зашивайте** решения на основе приведённых примеров.

### V.5 — Производительность и надёжность

Ваша реализация должна обеспечивать:

- **Почти идеальная точность:** 90%+ правильного выбора функций и извлечения аргументов
- **100% валидный JSON:** Каждый вывод должен быть разобираемым и соответствовать схеме
- **Разумная скорость:** Обработка всех тестовых промптов менее чем за 5 минут на стандартном оборудовании
- **Надёжная обработка ошибок:** Корректная обработка некорректных входных данных, отсутствующих файлов и граничных случаев

> [!NOTE]
> Модель Qwen3-0.6B имеет всего 500 миллионов параметров, но при правильном ограниченном декодировании она может достичь надёжности, сопоставимой со значительно более крупными моделями. Это демонстрирует силу структурного руководства по сравнению с размером модели.

### V.6 — Тестирование вашей реализации

Для проверки корректности вашего решения:

1. Убедитесь, что входные файлы находятся в каталоге `data/input/`
